## 每人都要能说清

1. A 是 TCP 服务端，B GUI 和 STM32 C 是两个客户端；C 上位机只走 UART。
2. A 计算 actual，B 计算 target，STM32 C 计算 available/limit/桨距/启停；三者不能互相冒充。
3. `session_id + step + seq` 用于会话、仿真步和命令幂等；UTC 是发生时间，`sim_time_s` 是仿真时间。
4. ACK 超时是“投递结果未知”，不换 seq 盲目重发；重连先做全量状态同步。
5. 断线处理：B 指数退避；C 连续失败软复位 ESP8266 并重建 Wi-Fi/TCP；A 写 WARNING 并非阻塞弹窗。
6. 何为硬件证据：CubeIDE 0 error、新烧录、真三机/热点/COM 口、断线恢复时间和对应日志；PC mock 不算。

## 常见提问的简短回答

- “为什么 B 目标不等于 A 实际？”：目标是调度指令，actual 还受 C 动作、能力、桨距、设备上下限和爬坡影响。
- “高风如何处理？”：风速达切出阈值 25 m/s 时 C 禁止风机运行/顺桨，A actual 根据动作与约束下降，B 由柴发补偿或显式记录缺电。
- “为什么虚拟环境不在 Git？”：虚拟环境不可移植且体积大，仓库固定 `requirements.txt` 和 Python 3.11 初始化脚本以可重现构建。
- “B 为什么不是三个默认进程？”：项目最终决策为 GUI 直接持有 TCP，网络连接与 ACK 轮询均非阻塞；兼容 I/O/compute 服务保留但不是正式启动链。这是第 13 项需主动说明的设计偏差。
